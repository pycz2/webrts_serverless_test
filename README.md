# WebRTC P2P чат без своего сервера

Proof of concept: два браузера в любых точках мира соединяются напрямую через WebRTC DataChannel и обмениваются текстом.
Весь проект — один статический файл `index.html` на GitHub Pages. Своего сервера нет.

Демо: https://pycz2.github.io/webrts_serverless_test/

## Как проверить (два компьютера, две сети)

1. **Хост** открывает страницу и нажимает «1. Создать приглашение».
2. Хост копирует ссылку и отправляет её собеседнику любым способом (Telegram, почта…). Вкладку **не закрывать**.
3. **Гость** открывает эту ссылку в браузере. Другой вариант: открыть сайт и вставить ссылку в поле «Вас пригласили?». Страница сразу показывает код-ответ.
4. Гость копирует код-ответ и отправляет его обратно хосту тем же способом. Вкладку **не закрывать**.
5. Хост вставляет код-ответ в поле и нажимает «Подключиться».
6. У обоих появляется чат. Первая строка показывает тип маршрута:
   - `host ↔ host` — одна локальная сеть;
   - `srflx ↔ …` — прямое соединение через интернет сквозь NAT (то, что нужно проверить);
   - `relay` — через TURN-ретранслятор ExpressTURN (запасной путь, если прямой не работает).

Статус наверху страницы: `new` → `connecting` → `connected`. Если статус `failed` — см. «Ограничения».

Одна ссылка = одно соединение. Для новой попытки обоим надо перезагрузить страницу (хост — без `#…` в адресе).

## Как это работает

WebRTC нужно три вещи:

| Что | Чем здесь закрыто |
|---|---|
| Узнать свой внешний IP:порт за NAT | публичные STUN-серверы Google (`stun.l.google.com:19302`) и Cloudflare |
| Обменяться описаниями соединения (SDP + ICE-кандидаты) — «сигналинг» | **вручную**: ссылка туда, код-ответ обратно |
| Передавать данные | напрямую браузер↔браузер, DataChannel (SCTP поверх DTLS/UDP, надёжный и упорядоченный, как TCP) |

Google STUN не передаёт сообщения между людьми — он только отвечает «твой внешний адрес такой-то».
Поэтому обмен описаниями нужен в обе стороны, и без сервера его делает человек: offer едет в ссылке (в `#hash`, на сервер не уходит), answer — кодом обратно.
Страница ждёт сбора всех ICE-кандидатов и пакует SDP через `deflate` + base64url, поэтому хватает одной ссылки и одного кода (~600 символов).

## Ограничения

- **Symmetric NAT / закрытый UDP.** Если обе стороны за symmetric NAT (часть мобильных операторов, корпоративные сети, CGNAT), прямое соединение невозможно — это ограничение NAT, а не кода.
  Для этого случая в `ICE_SERVERS` настроен TURN-ретранслятор `free.expressturn.com:3478` (UDP и TCP; бесплатный тариф, 1 ТБ/мес).
  Браузер включает его сам, только если прямые маршруты не работают. Трафик через TURN остаётся зашифрован DTLS: сервер пересылает байты, но не читает их.
  Логин TURN виден в коде страницы любому, поэтому кто угодно может израсходовать лимит. Для продукта нужны временные логины от своего бэкенда.
- Порт 443 у бесплатного ExpressTURN не отвечает. Если сеть пропускает только 443 (жёсткие корпоративные файрволы), нужен другой TURN с `turns:…:443`.
- Вкладки должны быть открыты, пока идёт обмен кодами. Хост должен вставить код-ответ в течение ~3 минут после того, как гость его получил (проверено: Chrome и Firefox соединяются после 180 с ожидания, Chrome не соединяется после 300 с). Если не успели — оба перезагружают страницу и начинают заново.
- Аутентификации нет: кто получил ссылку, тот и подключится (но только один).

## Локальный запуск и тест

```sh
python3 -m http.server 8000   # открыть http://localhost:8000 в двух вкладках
```

Автотест (два изолированных окна Chrome проходят весь сценарий, нужен установленный Google Chrome):

```sh
npm i --no-save playwright-core && node test.mjs
```

## Публикация на GitHub Pages

Settings → Pages → Source: «Deploy from a branch» → `gh-pages` / `/ (root)` → Save. Через минуту сайт доступен по адресу выше.
Обновить сайт: `git push origin main:gh-pages`.
